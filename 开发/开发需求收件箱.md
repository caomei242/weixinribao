## 2026-05-18 14:36｜产品助手｜微信反馈防漏收件箱 V1 一条龙返工

- 状态：待监工分派
- 来源线程：微信agent专项 产品助手 + office-hours 产品诊断
- 建议负责板块：真实试读审阅 / 防漏收件箱 / 群客户打标 / 草稿日报前台 / 转述摘要
- 目标页面 / 模块：微信反馈防漏收件箱 V1、今日防漏、试读消息、候选收件箱、群 / 客户打标、草稿日报、转述摘要、配置中心
- 背景：
  - 用户当前真实流程是草莓本人翻微信群 / 手机、截图、再转给产品 / 技术 / 运营。
  - 核心痛点不是“日报不够好看”，而是：如果忘记翻群，反馈就没有后续；需求要截图转述，非常麻烦。
  - 用户明确选择优先覆盖 A 防漏提醒、B 免截图转述、C 需求收件箱、D 日报草稿，并要求群 / 客户打标字段先都上，一条龙跑通后再实战调整。
  - office-hours 设计文档：`/Users/gd/.gstack/projects/agent/gd-main-design-20260518-143616.md`
- 产品定位：
  - V1 不再叫“日报系统”，而是 `微信反馈防漏收件箱`。
  - 日报是确认后的输出，不是第一步。
  - V1 只验一个真实群、最近 50 条、一条龙跑通。
- 需求：
  - 新增主入口 `微信反馈防漏收件箱`，围绕一条链路组织：试读 50 条 -> 消息明细 -> 发送人识别 -> 候选事项 -> 群 / 客户打标 -> 人工确认 -> 草稿日报 -> 转述摘要。
  - `今日防漏`页展示：今天跑没跑、读了哪个群、原始消息数、候选数、待确认数、风险数、草稿日报状态。
  - `试读消息`页展示最近 50 条原始消息明细：时间、发送人显示名、微信名 / 群昵称 / 备注名、身份判断、消息类型、消息内容、是否关联候选、风险标记。
  - `发送人识别`能力：无法解析微信名时显示 `未解析`，支持人工标记为我方 / 客户方 / 渠道方 / 未知，并支持加入我方人员别名或常用联系人。
  - `候选收件箱`展示系统抽取事项，支持确认、驳回、改类型、标风险、补负责人、补优先级、补下游同步对象、标记是否需要对外回复。
  - 候选详情必须能回看来源消息链，至少展示关联消息的时间、发送人、身份判断和内容；必要时展示前后上下文。
  - `群 / 客户打标`字段先都上：客户名称、群负责人、业务模块、客户阶段、群类型、常用联系人、回复注意事项。
  - 打标信息用于候选归属、日报分组、待办负责人建议、转述摘要和后续发消息辅助。
  - `草稿日报`必须在前台可查看，不能只弹文件路径；展示机器初稿 / 待审阅状态、生成时间、数据源、原始消息数、候选数、已确认数、待确认数、风险数。
  - 草稿日报里的事项能点回候选和消息证据。
  - `转述摘要`用于替代截图转发，支持生成给产品 / 技术 / 运营的脱敏摘要；转述版不得包含真实原文、敏感信息、wxid、key、salt、真实 DB 路径或 daemon 原始日志。
  - 顶部旧导出按钮需弱化或并入新主线，避免用户绕过审阅直接导出。
  - 配置中心补起始日期时间、结束日期时间、最近条数，快捷项 `最近50条 / 最近2小时 / 今天` 会同步更新范围。

- 验收标准：
  - 用户能用一个真实群完成完整链路：试读 50 条 -> 看消息明细 -> 识别发送人 -> 确认候选 -> 打标 -> 看草稿日报 -> 生成转述摘要。
  - 页面一眼区分原始消息数量和候选事项数量。
  - 用户能回答“谁在什么时间说了什么”，不能只看到候选摘要。
  - 任一候选都能回看来源消息链。
  - 任一发送人都能看到显示名和身份判断；无法解析时提供人工映射。
  - 群 / 客户打标字段全量可编辑并保存；保存不触发真实采集。
  - 草稿日报在前台可看，并标明机器初稿 / 待审阅 / 不可外发。
  - 转述摘要能替代截图转发，并区分给产品 / 技术 / 运营。
  - 默认 `real_read_enabled=false` 不得被持久改成开启。
  - 不读取白名单外会话，不自动回复，不外发，不写正式日报 / 正式待办池 / Obsidian 正式区。
  - 状态卡、回报队列、测试日志、产品走查不得摘录真实消息正文、真实会话列表、wxid、key、salt、真实 DB 路径或 daemon 原始日志。
- 不做事项：
  - 不做多群全量长期运行。
  - 不做 OCR / 语音识别 / 图片内容理解。
  - 不调用外部 LLM 改写客户原文。
  - 不自动给客户回复。
  - 不自动写正式待办池或正式日报。
  - 不把机器初稿当正式日报。
- 风险 / 备注：
  - `wx-cli` 是否能稳定返回群成员昵称 / 备注名 / 微信昵称，需要开发按实际输出字段验证；如果不能解析，必须显示未解析并提供人工映射。
  - 群 / 客户打标先全量上字段，但 V1 只要求一个真实群跑通，不要求多群批量管理。
  - 下一棒建议：监工将当前零散返工合并为 `微信反馈防漏收件箱 V1` 大返工包，优先派前台 / 后端联动开发助手；完成后派测试审查助手复核真实读取边界、本地 UI 原文展示边界、转述版脱敏和正式写入禁用。

## 2026-05-18 14:13｜产品助手｜真实试读消息明细与发送人可审阅返工

- 状态：待监工分派
- 来源线程：微信agent专项 产品助手
- 建议负责板块：最近真实试读 / 消息明细 / 发送人识别 / 前台视觉还原 / 候选证据链
- 目标页面 / 模块：微信反馈采集工作台配置中心、每日总控、最近真实试读、候选事项详情、消息明细抽屉 / 表格
- 背景：
  - 用户实战反馈：外观和原型图差距仍明显；页面只看到 3 条候选事项，看不到完整最近 50 条消息明细；也看不到是谁说了什么。
  - 产品判断：当前“3 条”是候选事项数量，不是原始消息数量。实战审阅必须同时展示“原始消息明细”和“抽取候选事项”，并把候选和来源消息串起来。
  - 发送人识别是人工确认前提：如果只给摘要，不给微信昵称 / 群昵称 / 备注名 / 身份判断，用户无法判断需求是否成立、是否我方已回复、是否需要对外回复。
- 需求：
  - 在最近真实试读区域明确区分两类数量：`原始消息：最多 50 条`、`候选事项：N 条`，不能只展示候选数让用户误以为只读到 3 条消息。
  - 新增 `消息明细`视图 / 抽屉 / 表格，默认展示本次试读范围内的原始消息列表。
  - 消息明细字段至少包括：时间、发送人显示名、身份判断、消息类型、消息内容、所属会话、是否命中候选、关联候选编号、风险标记。
  - 发送人显示名优先级：群成员昵称 / 微信昵称 / 备注名 / wx-cli 可解析名称；如果只能拿到内部标识，则显示 `未解析微信名`，并给出人工映射入口。
  - 新增 `发送人识别`辅助区：按本次试读出现的发送人聚合，展示发送人显示名、出现次数、当前身份、是否匹配我方人员别名、可手动标记为我方 / 客户方 / 渠道方 / 未知。
  - 我方人员名单配置页支持从本次试读发送人一键加入别名；保存后不自动采集，只影响后续身份判断和当前本地重算 / 刷新。
  - 候选事项详情必须展示其来源消息链：至少可看到关联消息的时间、发送人显示名、身份判断和消息内容；必要时提供前后若干条上下文。
  - 最近真实试读候选不能只停留在摘要卡片：必须支持进入本地待确认流，或在导出模板中选择数据源 `当前工作台 / 最近真实试读`。
  - 新增 `草稿日报`前台查看入口：用户生成待审日报 / 待沉淀草稿后，必须能在前台看到草稿内容、生成时间、数据源、候选数量、风险数量和本地导出状态。
  - 草稿日报入口至少支持：查看最新草稿、刷新预览、重新生成、打开导出模板、查看关联候选 / 消息明细。
  - 草稿日报必须区分：`机器初稿`、`人工已确认`、`待沉淀草稿`、`不可外发`，不能让用户误以为已经是正式日报。
  - 前台视觉需要重新贴近已确认原型图：左侧清晰导航、顶部状态条、主区消息明细 + 候选事项双栏、右侧详情 / 发送人识别，不得退回调试表格或普通弹窗堆叠。
  - 顶部或试读区加入解释文案：`50 条是原始消息，候选事项是系统从消息中抽取出的可处理事项`。

- 验收标准：
  - 用户能在前台一眼区分：读取了多少原始消息、抽出了多少候选事项。

  - 每条消息都尽量展示微信显示名；若无法解析，必须明确显示未解析原因和人工映射入口，不能静默空白。
  - 用户能从候选事项跳回来源消息，也能从消息看到是否生成候选。

  - 最近真实试读候选能进入本地待确认流，或导出模板能选择最近真实试读作为数据源；不能再出现“试读有候选但模板预览为空”的体验。
  - 草稿日报能在前台直接查看；不能只弹出文件路径，也不能要求用户去文件夹里找 Markdown。

  - 不做 OCR、语音识别、图片内容识别。
  - 不把无法解析微信名的发送人强行判断为客户方。
- 风险 / 备注：
  - `wx-cli` 是否能直接返回群成员昵称、备注名或微信昵称，需要开发在适配层按实际输出字段做兼容；如果字段缺失，第一版必须提供人工映射。
  - 本地 UI 可以为人工审阅展示消息内容，但任何监工回报、状态卡、产品走查和测试日志仍不得摘录真实原文。
  - 下一棒建议：监工返工开发助手补消息明细 / 发送人识别 / 候选证据链 / 试读数据源闭环；完成后派测试审查助手复核字段白名单、真实读取边界和前台可用性。
