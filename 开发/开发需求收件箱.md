## 2026-05-18 14:36｜产品助手｜微信反馈防漏收件箱 V1 一条龙返工

- 状态：待监工分派
- 来源线程：微信agent专项 产品助手 + office-hours 产品诊断
- 建议负责板块：真实试读审阅 / 防漏收件箱 / 群客户打标 / 草稿日报前台 / 转述摘要
- 目标页面 / 模块：微信反馈防漏收件箱 V1、今日防漏、试读消息、候选收件箱、群 / 客户打标、草稿日报、转述摘要、配置中心
- 背景：
  - 用户当前真实流程是草莓本人翻微信群 / 手机、截图、再转给产品 / 技术 / 运营。
  - 核心痛点不是“日报不够好看”，而是：如果忘记翻群，反馈就没有后续；需求要截图转述，非常麻烦。
  - 用户明确选择优先覆盖 A 防漏提醒、B 免截图转述、C 需求收件箱、D 日报草稿，并要求群 / 客户打标字段先都上，一条龙跑通后再实战调整。
  - office-hours 设计文档：`/Users/gd/.gstack/projects/agent/gd-main-design-20260518-143616.md`
- 产品定位：
  - V1 不再叫“日报系统”，而是 `微信反馈防漏收件箱`。
  - 日报是确认后的输出，不是第一步。
  - V1 只验一个真实群、最近 50 条、一条龙跑通。
- 需求：
  - 新增主入口 `微信反馈防漏收件箱`，围绕一条链路组织：试读 50 条 -> 消息明细 -> 发送人识别 -> 候选事项 -> 群 / 客户打标 -> 人工确认 -> 草稿日报 -> 转述摘要。
  - `今日防漏`页展示：今天跑没跑、读了哪个群、原始消息数、候选数、待确认数、风险数、草稿日报状态。
  - `试读消息`页展示最近 50 条原始消息明细：时间、发送人显示名、微信名 / 群昵称 / 备注名、身份判断、消息类型、消息内容、是否关联候选、风险标记。
  - `发送人识别`能力：无法解析微信名时显示 `未解析`，支持人工标记为我方 / 客户方 / 渠道方 / 未知，并支持加入我方人员别名或常用联系人。
  - `候选收件箱`展示系统抽取事项，支持确认、驳回、改类型、标风险、补负责人、补优先级、补下游同步对象、标记是否需要对外回复。
  - 候选详情必须能回看来源消息链，至少展示关联消息的时间、发送人、身份判断和内容；必要时展示前后上下文。
  - `群 / 客户打标`字段先都上：客户名称、群负责人、业务模块、客户阶段、群类型、常用联系人、回复注意事项。
  - 打标信息用于候选归属、日报分组、待办负责人建议、转述摘要和后续发消息辅助。
  - `草稿日报`必须在前台可查看，不能只弹文件路径；展示机器初稿 / 待审阅状态、生成时间、数据源、原始消息数、候选数、已确认数、待确认数、风险数。
  - 草稿日报里的事项能点回候选和消息证据。
  - `转述摘要`用于替代截图转发，支持生成给产品 / 技术 / 运营的脱敏摘要；转述版不得包含真实原文、敏感信息、wxid、key、salt、真实 DB 路径或 daemon 原始日志。
  - 顶部旧导出按钮需弱化或并入新主线，避免用户绕过审阅直接导出。
  - 配置中心补起始日期时间、结束日期时间、最近条数，快捷项 `最近50条 / 最近2小时 / 今天` 会同步更新范围。

- 验收标准：
  - 用户能用一个真实群完成完整链路：试读 50 条 -> 看消息明细 -> 识别发送人 -> 确认候选 -> 打标 -> 看草稿日报 -> 生成转述摘要。
  - 页面一眼区分原始消息数量和候选事项数量。
  - 用户能回答“谁在什么时间说了什么”，不能只看到候选摘要。
  - 任一候选都能回看来源消息链。
  - 任一发送人都能看到显示名和身份判断；无法解析时提供人工映射。
  - 群 / 客户打标字段全量可编辑并保存；保存不触发真实采集。
  - 草稿日报在前台可看，并标明机器初稿 / 待审阅 / 不可外发。
  - 转述摘要能替代截图转发，并区分给产品 / 技术 / 运营。
  - 默认 `real_read_enabled=false` 不得被持久改成开启。
  - 不读取白名单外会话，不自动回复，不外发，不写正式日报 / 正式待办池 / Obsidian 正式区。
  - 状态卡、回报队列、测试日志、产品走查不得摘录真实消息正文、真实会话列表、wxid、key、salt、真实 DB 路径或 daemon 原始日志。
- 不做事项：
  - 不做多群全量长期运行。
  - 不做 OCR / 语音识别 / 图片内容理解。
  - 不调用外部 LLM 改写客户原文。
  - 不自动给客户回复。
  - 不自动写正式待办池或正式日报。
  - 不把机器初稿当正式日报。
- 风险 / 备注：
  - `wx-cli` 是否能稳定返回群成员昵称 / 备注名 / 微信昵称，需要开发按实际输出字段验证；如果不能解析，必须显示未解析并提供人工映射。
  - 群 / 客户打标先全量上字段，但 V1 只要求一个真实群跑通，不要求多群批量管理。
  - 下一棒建议：监工将当前零散返工合并为 `微信反馈防漏收件箱 V1` 大返工包，优先派前台 / 后端联动开发助手；完成后派测试审查助手复核真实读取边界、本地 UI 原文展示边界、转述版脱敏和正式写入禁用。

## 2026-05-18 14:13｜产品助手｜真实试读消息明细与发送人可审阅返工

- 状态：待监工分派
- 来源线程：微信agent专项 产品助手
- 建议负责板块：最近真实试读 / 消息明细 / 发送人识别 / 前台视觉还原 / 候选证据链
- 目标页面 / 模块：微信反馈采集工作台配置中心、每日总控、最近真实试读、候选事项详情、消息明细抽屉 / 表格
- 背景：
  - 用户实战反馈：外观和原型图差距仍明显；页面只看到 3 条候选事项，看不到完整最近 50 条消息明细；也看不到是谁说了什么。
  - 产品判断：当前“3 条”是候选事项数量，不是原始消息数量。实战审阅必须同时展示“原始消息明细”和“抽取候选事项”，并把候选和来源消息串起来。
  - 发送人识别是人工确认前提：如果只给摘要，不给微信昵称 / 群昵称 / 备注名 / 身份判断，用户无法判断需求是否成立、是否我方已回复、是否需要对外回复。
- 需求：
  - 在最近真实试读区域明确区分两类数量：`原始消息：最多 50 条`、`候选事项：N 条`，不能只展示候选数让用户误以为只读到 3 条消息。
  - 新增 `消息明细`视图 / 抽屉 / 表格，默认展示本次试读范围内的原始消息列表。
  - 消息明细字段至少包括：时间、发送人显示名、身份判断、消息类型、消息内容、所属会话、是否命中候选、关联候选编号、风险标记。
  - 发送人显示名优先级：群成员昵称 / 微信昵称 / 备注名 / wx-cli 可解析名称；如果只能拿到内部标识，则显示 `未解析微信名`，并给出人工映射入口。
  - 新增 `发送人识别`辅助区：按本次试读出现的发送人聚合，展示发送人显示名、出现次数、当前身份、是否匹配我方人员别名、可手动标记为我方 / 客户方 / 渠道方 / 未知。
  - 我方人员名单配置页支持从本次试读发送人一键加入别名；保存后不自动采集，只影响后续身份判断和当前本地重算 / 刷新。
  - 候选事项详情必须展示其来源消息链：至少可看到关联消息的时间、发送人显示名、身份判断和消息内容；必要时提供前后若干条上下文。
  - 最近真实试读候选不能只停留在摘要卡片：必须支持进入本地待确认流，或在导出模板中选择数据源 `当前工作台 / 最近真实试读`。
  - 新增 `草稿日报`前台查看入口：用户生成待审日报 / 待沉淀草稿后，必须能在前台看到草稿内容、生成时间、数据源、候选数量、风险数量和本地导出状态。
  - 草稿日报入口至少支持：查看最新草稿、刷新预览、重新生成、打开导出模板、查看关联候选 / 消息明细。
  - 草稿日报必须区分：`机器初稿`、`人工已确认`、`待沉淀草稿`、`不可外发`，不能让用户误以为已经是正式日报。
  - 前台视觉需要重新贴近已确认原型图：左侧清晰导航、顶部状态条、主区消息明细 + 候选事项双栏、右侧详情 / 发送人识别，不得退回调试表格或普通弹窗堆叠。
  - 顶部或试读区加入解释文案：`50 条是原始消息，候选事项是系统从消息中抽取出的可处理事项`。

- 验收标准：
  - 用户能在前台一眼区分：读取了多少原始消息、抽出了多少候选事项。

  - 每条消息都尽量展示微信显示名；若无法解析，必须明确显示未解析原因和人工映射入口，不能静默空白。
  - 用户能从候选事项跳回来源消息，也能从消息看到是否生成候选。

  - 最近真实试读候选能进入本地待确认流，或导出模板能选择最近真实试读作为数据源；不能再出现“试读有候选但模板预览为空”的体验。
  - 草稿日报能在前台直接查看；不能只弹出文件路径，也不能要求用户去文件夹里找 Markdown。

  - 不做 OCR、语音识别、图片内容识别。
  - 不把无法解析微信名的发送人强行判断为客户方。
- 风险 / 备注：
  - `wx-cli` 是否能直接返回群成员昵称、备注名或微信昵称，需要开发在适配层按实际输出字段做兼容；如果字段缺失，第一版必须提供人工映射。
  - 本地 UI 可以为人工审阅展示消息内容，但任何监工回报、状态卡、产品走查和测试日志仍不得摘录真实原文。
  - 下一棒建议：监工返工开发助手补消息明细 / 发送人识别 / 候选证据链 / 试读数据源闭环；完成后派测试审查助手复核字段白名单、真实读取边界和前台可用性。

- 实现方案草案：
  - 总体架构：

```text
公司成员
  -> Slock 里的「微信日报值班 Agent」
  -> Windows 挂机机上的 agent bridge
  -> Windows 本地日报服务 http://127.0.0.1:8765
  -> 本地 SQLite / 本机配置 / wx-cli / 微信登录状态
```

  - Windows 本地日报服务继续负责真实业务：读取白名单群、保存本地消息、生成候选、生成日报、维护群档案和我方人员。
  - 新增 `agent bridge` 小进程或脚本，和 Windows 本地服务跑在同一台电脑上；它只调用本机接口，不自己读微信数据库。
  - Slock agent 不直接碰微信、不直接碰 SQLite，只通过 `agent bridge` 获取允许暴露的数据。
  - 本地服务需新增一组给 agent 用的脱敏接口：

```text
GET  /api/agent/status
返回：服务在线、当前机器、代码版本、最后采集时间、真实读取状态、监控群数、失败群数

GET  /api/agent/daily
返回：日报状态、沉淀状态、今天最要跟、待确认数、历史未收口数、监控缺口

GET  /api/agent/followups
返回：未完成跟进列表，只含摘要、客户/群、状态、负责人、风险级别，不含真实原文

GET  /api/agent/groups
返回：监控群状态、是否启用、是否纳入日报、失败原因、配置完整度

POST /api/agent/actions
输入：动作类型、对象 id、操作人、二次确认 token
用于：确认候选、标记已收口、转技术、归档群等受控动作
```

  - 第一阶段先不做复杂自然语言理解：Slock agent 先用固定命令 / 菜单，例如 `今日日报`、`未完成跟进`、`监控状态`、`失败群`、`刷新日报`。
  - 第一阶段固定频道只自动推送状态卡，不自动推送具体事项正文；`未完成跟进` 这类明细必须由有权限的人主动查询。
  - 第二阶段再做自由问答，把用户问题解析成固定查询，例如 `某客户还有什么没收口` -> 查询 followups。
  - 第三阶段才做操作回写，例如在 Slock 里确认候选、转给技术、归档群；所有高风险动作必须二次确认。
  - 权限实现先从配置文件或本地管理页开始，不急着接公司复杂组织架构；至少要能配置 `查看者 / 确认者 / 管理员 / 负责人`。
  - 审计记录写在 Windows 本地，不写入 Slock 云端；记录操作人、动作、对象、时间、结果和错误码，不记录真实消息正文。
  - 如果 Windows 服务离线，Slock agent 只能返回离线状态和最近心跳，不能猜日报内容。
  - 如果 Slock 暂时没有稳定插件 / webhook 能直接连本机，则先实现 `agent bridge` 定时把摘要推到 Slock；交互式问答作为第二阶段。

- 验收标准：
  - 团队成员不需要通过用户 Mac，就能在 Slock 固定入口看到日报状态和待跟进摘要。
  - Windows 挂机机是唯一真实读取执行环境；页面能看出当前执行机器不是 Mac。
  - Slock agent 能回答日报状态、未完成跟进、监控失败和候选待确认等基础问题。
  - Slock 推送不包含真实微信原文、真实会话列表、wxid、key、salt、真实 DB 路径或 daemon 原始日志。
  - 高风险动作，例如删除监控群、开启真实读取、外发摘要、确认沉淀，必须二次确认或限制权限。
  - 多人操作有本地审计记录，可追溯谁确认了候选、谁改了群配置、谁触发了日报推送。
  - Windows 服务离线时，Slock agent 能明确提示 `执行机器离线 / 服务不可用 / 最近心跳时间`，而不是让用户误以为系统正常。
- 不做事项：
  - 不把真实微信数据库或真实消息正文同步到 Slock 云端。
  - 不让 Slock agent 直接绕过 Windows 本机服务读取微信。
  - 不默认允许所有公司成员修改监控群、我方人员或真实读取开关。
  - 不自动外发客户回复。
  - 不依赖用户 Mac 作为长期运行节点。
- 风险 / 备注：
  - 这条需求标志着产品形态从 `个人本地工具` 升级为 `公司多人协作值班系统`。
  - 实现上建议分阶段：第一阶段只做 Windows 服务状态 + Slock 日报推送；第二阶段做 Slock 问答；第三阶段做多人权限和操作回写。

## 2026-05-19 17:34｜产品助手｜日报生成即时反馈：点击后立刻看到进度，不让用户干等

- 状态：待监工分派
- 来源线程：微信agent专项 产品助手
- 建议负责板块：日报中心 / 前台交互状态 / 后端生成状态 / 错误提示
- 目标页面 / 模块：日报中心、生成/刷新日报按钮、日报全文区域、日报状态卡、右侧状态区
- 背景：
  - 用户在日报中心点击 `生成/刷新日报` 后反馈：日报生成太慢，需要等一会才出现。
  - 当前体验的问题不是单纯性能，而是点击后页面没有足够即时反馈：用户不知道系统正在生成、已经卡住、还是没点到。
  - 日报中心是每天第一屏高频入口，生成动作必须有明确过程反馈和失败出口。
- 需求：
  - P0：点击 `生成/刷新日报` 后，按钮立即进入 `生成中...` 状态，并禁用重复点击；页面不得长时间保持空白。
  - P0：日报全文区域立即显示生成进度态，例如 `正在整理今日候选、未完成跟进和监控缺口...`，而不是继续显示大面积空白。
  - P0：生成中状态至少展示：开始时间、数据来源、候选数量、预计下一步、可取消 / 刷新状态。
  - P0：生成完成后自动替换为日报全文，不要求用户再手动刷新页面。
  - P0：生成失败时在日报全文区域显示人话错误：失败原因、是否可重试、下一步做什么；不能只显示技术错误码。
  - P0：如果已有上一版日报，重新生成时保留上一版可读内容，并在顶部提示 `正在生成新版`，不要把正文清空成白板。
  - P1：后端提供生成状态，前台轮询或订阅状态：`idle / generating / generated / failed`，并返回生成时间、错误原因、数据源、候选数。
  - P1：超过合理时间仍未完成时显示慢任务提示，例如 `生成时间较长，可稍后回来；完成后会自动更新`。
  - P1：生成按钮旁显示最近一次生成时间和结果，帮助判断是不是已经生成过。

- 验收标准：
  - 点击 `生成/刷新日报` 后 1 秒内能看到明确生成中状态。
  - 生成过程中按钮不会允许连续重复提交。
  - 页面不会出现长时间空白区域；即使没有日报，也有生成进度或失败提示。
  - 生成完成后日报全文自动出现，不需要用户手动刷新浏览器。
  - 生成失败时用户能看懂为什么失败和下一步怎么做。
  - 重新生成时不清空上一版日报正文，避免用户以为内容丢了。
  - 状态文案不出现 `pending / workspace / local_markdown / error_code` 这类机器词作为主反馈。
- 不做事项：
  - 不自动写正式日报或正式待办池。
  - 不把生成中的机器初稿外发到 Slock 或其他系统。
  - 不为了速度绕过人工确认和安全边界。
- 风险 / 备注：

## 2026-05-20｜长期真实读取授权模式

- 来源：总控线程根据用户 2026-05-20 19:28 明确授权方向整理。
- 需求背景：
  - 当前已完成的一次性真实试验契约是 `one_time_only=true`，需要 `execute_once` 与一次性授权标记。
  - 用户明确表示“不用一次性授权，不用这么保守，直接长期授权”。
  - 因此后续不应继续把真实读取能力设计成每次一张一次性通行证，而应做成可配置、可暂停、可审计的长期授权模式。
- 产品目标：
  - 在测试微信号 / Windows 正式挂机机上，允许系统长期读取已配置监控群白名单范围内的真实消息，用于候选提取和日报生成。
  - 长期授权必须是系统内一等能力，不允许靠 Windows 现场手工绕过接口跑 `wx history/search/export/new-messages`。
  - 授权范围可以配置：lookback days、群范围、单群消息上限、总消息上限、批次上限、运行频率或手动触发。
- 后端/API 最小能力：
  - 配置结构支持 `authorization_mode=persistent` 或等价字段，区别于 `one_time_only`。
  - `/api/status` 和 `/api/config-center` 暴露长期授权状态、范围、上限、暂停状态、最近一次运行摘要和错误码。
  - `/api/real-trial/run` 或新接口支持长期授权模式下无需一次性 token 执行，但仍必须校验长期授权已开启、测试微信号确认、群白名单、窗口和数量上限。
  - 长期授权模式下默认只写本项目候选 / 本地数据库，不自动写正式日报、正式待办池、Obsidian 正式区或外部系统。
  - 所有回报和日志默认只给 count/status/error_code/字段存在性，不返回真实正文、真实群名、真实会话、成员、客户名单、wxid/key/salt、DB 路径、IP 或 daemon 原始日志。
- 前台/UI 最小能力：
  - 配置中心或 Windows readiness 页面显示“长期真实读取授权”状态：未开启 / 已开启 / 已暂停 / 错误。
  - 提供清楚的启用、暂停、保存上限和读回验证入口。
  - 明确显示当前范围：启用监控群数量、lookback days、消息上限、最近运行状态；不展示敏感明细。
- 测试 / 验收：
  - fixture / fake executor 覆盖 persistent 模式：授权未开 blocked、已开 dry-run、已开执行路径、暂停后 blocked、上限超出 blocked。
  - Windows 发布前必须确认 `HEAD/origin/main` 与 Windows `release_head` 包含长期授权字段。
  - Windows 回归先验字段存在性和 dry-run，再由用户决定是否开始长期真实读取；执行回传仍只允许 count/status/error_code。
- 不做事项：
  - 不把长期授权等同于自动外发、自动回复、自动写正式日报或正式待办池。
  - 不允许 Windows 现场手工直接跑 forbidden wx 命令替代系统接口。
  - 不在回报队列、状态卡、测试日志或聊天里粘贴真实消息正文或敏感明细。
- 建议拆分：
  - 先派后端/API：长期授权配置契约与执行门禁。
  - 再派前台/UI：配置入口和状态读回。
  - 再派测试审查：字段白名单、fake 执行、长期授权关闭/暂停/上限边界。
  - 最后再派 Windows：拉取发布版并做长期授权 dry-run / 小范围首跑。
