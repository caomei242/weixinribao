# 微信反馈采集工作台技术方案

更新时间：2026-05-15 15:10 CST

任务标记：`监工派工：2026-05-15 15:09｜架构方案｜微信反馈采集工作台技术方案`

## 1. 目标与边界

第一版目标是做一个本机运行的“采集、去重、候选抽取、人工确认、Markdown 导出”闭环。Mac 只作为测试环境，长期运行目标是 Windows 24 小时挂机机。

本方案严格遵守产品边界：

- 不接企微官方接口，只基于 `wx-cli` 能读取到的本地微信数据。
- 不调用外部 LLM，不把客户原文发出本机。
- 不自动回复客户、渠道或内部群。
- 不自动写入正式待办池，只导出 Markdown 供人工确认和后续沉淀。
- 不做 OCR、语音识别、图片内容理解或文件正文解析。
- 报价、合同、金额、投诉、敏感客户信息、需要对外回复的内容只能进入风险候选或待确认区，不得自动写成已确认结论。

## 2. 第一版推荐技术栈

### 2.1 本地后台

推荐：Python 3.12 + FastAPI + SQLite。

理由：

- Windows 长期挂机机部署简单，不需要浏览器自动化或桌面 UI 权限。
- FastAPI 可同时承载本地网页、配置 API、采集 API、导出 API。
- SQLite 适合单机、单用户、可备份、可检查的本地数据。
- 后续如要做 Windows 服务或计划任务，Python 入口易包装。

第一版不建议上 Electron、Docker、PostgreSQL、消息队列或外部任务系统；这些会增加部署和排障成本。

### 2.2 前端页面

推荐：本地静态 HTML + CSS + 原生 JavaScript，由 FastAPI 托管。

第一版页面包括：

- 工作台页：今日待确认事项、筛选区、候选列表、右侧确认表单。
- 配置页：白名单会话、我方人员名单、群负责人、客户/渠道/模块映射。
- 导出预览页：日报预览、待办预览、导出按钮。

第一版不引入 React/Vite 构建链，除非开发助手判断表单复杂度明显超出原生 JS。这样 Windows 部署时只需要 Python 运行环境和 `wx-cli`。

### 2.3 SQLite

推荐文件位置：

- 开发测试：`data/wechat_feedback.sqlite3`
- Windows 生产：由 `config/app.yaml` 指定绝对路径，例如 `D:\wechat-agent\data\wechat_feedback.sqlite3`

SQLite 必须开启：

- `PRAGMA foreign_keys = ON`
- WAL 模式：`PRAGMA journal_mode = WAL`
- 关键唯一索引：原始消息去重键、候选事项聚合键、导出记录日期/类型

### 2.4 配置文件

推荐：`config/app.yaml`，提交 `config/app.example.yaml`，真实配置不提交。

配置内容：

- `app.host` / `app.port`
- `database.path`
- `wx_cli.mode`: `fixture` 或 `real`
- `wx_cli.binary`: `wx` 或 Windows 绝对路径
- `wx_cli.timeout_seconds`
- `wx_cli.fixture_dir`
- `collector.interval_minutes`
- `collector.lookback_minutes`
- 白名单会话、客户/渠道/模块映射
- 我方人员名单与别名
- 风险关键词
- 导出目录

### 2.5 Markdown 导出

推荐：后台按模板生成 Markdown 文件，不写入正式日报或待办池。

默认导出目录：

- 开发测试：`exports/YYYY-MM-DD/`
- Windows 生产：由配置指定，例如 `D:\wechat-agent\exports\2026-05-15\`

文件名：

- `2026-05-15 微信反馈日报.md`
- `2026-05-15 待跟进事项.md`

导出后记录到 `export_records`，包括导出类型、日期、文件路径、包含事项、生成时间和模板版本。

### 2.6 Windows 长期挂机方式

第一版推荐 Windows 任务计划程序，不先做 Windows Service。

运行方式：

- 开机后启动后台：任务计划程序执行 `python -m wechat_feedback_app serve --config D:\wechat-agent\config\app.yaml`
- 定时采集：后台内置轻量 scheduler，每 30-60 分钟执行一次；同时页面提供“立即采集”。
- 可选兜底：另建任务计划程序每天 08:00 启动/检查后台进程。

Windows 部署目录建议：

```text
D:\wechat-agent\
  app\
  config\app.yaml
  data\wechat_feedback.sqlite3
  exports\
  logs\
  fixtures\
```

## 4. `wx-cli` 调用策略

### 4.1 适配层原则

所有 `wx-cli` 调用必须经过 `wx_cli_adapter.py`，业务流程不得直接拼命令。

适配层输出统一的内部结构：

```json
{
  "session_external_id": "string",
  "session_name": "string",
  "message_external_id": "string|null",
  "local_id": "string|null",
  "sender_display_name": "string",
  "sender_raw_id": "string|null",
  "sent_at": "2026-05-15T14:30:00+08:00",
  "message_type": "text",
  "content_text": "string",
  "raw_payload": {}
}
```

适配层负责：

- 命令路径解析。
- 超时与重试。
- stdout/stderr 捕获到后台日志。
- YAML/JSON 输出解析；优先要求 `--json`。
- 将 `wx-cli` 输出字段映射为内部字段。
- 隐藏真实模式和 fixture 模式差异。

### 4.2 fixture 模式

fixture 模式是第一棒开发的默认模式，必须先跑通。

行为：

- 从 `fixtures/wx_messages.sample.json` 读取模拟消息。
- 模拟多个白名单会话、白名单外会话、重复消息、风险消息、我方/客户方/未知发送方。
- 返回结构与真实模式完全一致。
- UI 顶部显示 `模式：fixture`，避免误以为正在读取真实微信。

验收：

- 不需要本机微信、不需要 `wx-cli`、不读取真实聊天库。
- 可以重复采集同一 fixture，不重复写入原始消息和候选事项。

### 4.3 真实模式

真实模式只在配置显式设置 `wx_cli.mode: real` 后启用。

参考已知 `wx-cli` 能力：它是读取本地 WeChat 4.x 数据的 Rust CLI，命令面包含 `sessions`、`history`、`new_messages`、`members` 等，默认 YAML 输出并支持 `--json`；运行形态有 CLI 和 daemon 两类。

真实模式建议调用序列：

1. `wx --version` 或等价命令，确认二进制可执行。
2. `wx sessions --json`，获取会话列表并与白名单配置匹配。
3. 对每个白名单会话调用历史/增量消息命令，优先用时间窗口或游标参数；如果当前 `wx-cli` 不支持稳定游标，则使用 lookback 窗口加本地去重兜底。
4. 将命令结果标准化为内部消息结构。

注意：

- 不在第一版里自动执行 `wx init`，只在连接测试中给出缺失提示和人工操作建议。
- 不要求开发助手读取真实微信数据库。
- Windows 上如 `wx-cli` 使用 daemon 或 named pipe，仍由适配层隔离，不让采集流程感知。

### 4.4 连接测试

配置页提供“测试 wx-cli 连接”按钮。

返回状态：

- `ok`: 二进制可执行，能列出会话或返回可解析输出。
- `missing_binary`: 找不到 `wx` 或配置路径错误。
- `not_initialized`: 需要先人工初始化 `wx-cli`。
- `wechat_not_running`: 微信未登录或本地数据不可读。
- `permission_denied`: 权限不足。
- `parse_error`: 输出格式变化或非 JSON。
- `timeout`: 命令超时。

页面显示：

- 简短原因。
- 最近一次成功采集时间。
- 降级状态：保留上次已采集数据，可继续审阅和导出历史已确认事项。

### 4.5 不可用时降级

当真实模式失败：

- 不清空现有数据。
- 不自动切换到 fixture 并混入正式库。
- 记录一条失败的 `collection_runs`。
- 工作台顶部显示失败原因。
- 允许继续人工确认已有候选事项。
- 允许导出已有确认事项。
- 禁止把失败窗口标记为成功采集。

## 5. 数据结构设计

### 5.1 `sessions`

会话配置与 `wx-cli` 会话映射。

字段：

- `id`: 本地主键
- `external_id`: `wx-cli` 会话 id 或可稳定识别字段
- `display_name`: 微信会话名
- `customer_name`
- `channel_name`
- `module_name`
- `owner_name`
- `is_whitelisted`
- `enabled`
- `last_success_at`
- `last_cursor`
- `created_at`
- `updated_at`

索引：

- `unique(external_id)`
- `index(is_whitelisted, enabled)`

### 5.2 `people_aliases`

我方人员与别名。

字段：

- `id`
- `person_name`
- `alias`
- `role`: `internal` / `customer` / `channel` / `unknown`
- `enabled`

索引：

- `unique(alias, role)`

第一版主要维护我方人员；非我方默认按会话映射识别为客户方/渠道方/未知。

### 5.3 `raw_messages`

原始消息只做本地留存和证据引用。

字段：

- `id`
- `session_id`
- `message_external_id`
- `local_id`
- `sender_display_name`
- `sender_role`: `internal` / `customer` / `channel` / `unknown`
- `sent_at`
- `message_type`
- `content_text`
- `content_hash`
- `dedupe_key`
- `raw_payload_json`
- `collection_run_id`
- `created_at`

去重键规则：

1. 优先：`session_external_id + message_external_id`
2. 次选：`session_external_id + local_id`
3. 兜底：`session_external_id + sent_at + sender_display_name + sha256(normalized_content_text)`

索引：

- `unique(dedupe_key)`
- `index(session_id, sent_at)`
- `index(content_hash)`

### 5.4 `candidate_items`

结构化候选事项。

字段：

- `id`
- `item_code`: 如 `R-001`、`B-001`、`F-001`
- `item_type`: `requirement` / `bug` / `consultation` / `conclusion` / `followup`
- `status`: `pending` / `confirmed` / `rejected`
- `risk_level`: `none` / `low` / `high`
- `risk_tags_json`: 报价、合同、金额、投诉、敏感信息、需对外回复等
- `customer_name`
- `channel_name`
- `module_name`
- `title`
- `summary`
- `suggested_downstream`: `product` / `tech` / `ops` / `manual`
- `aggregate_key`
- `first_seen_at`
- `last_seen_at`
- `created_at`
- `updated_at`

候选聚合键：

```text
item_type + customer_name + channel_name + module_name + sha256(normalized_summary_or_keywords)
```

第一版不用外部 LLM，摘要只能来自规则模板和关键词，不做“智能定性”。风险项默认保持 `pending`。

### 5.5 `candidate_item_messages`

候选事项与原始消息的证据关系。

字段：

- `item_id`
- `raw_message_id`
- `evidence_order`

索引：

- `unique(item_id, raw_message_id)`

### 5.6 `manual_reviews`

人工确认记录。

字段：

- `id`
- `item_id`
- `review_status`: `pending` / `confirmed` / `rejected`
- `owner_name`
- `priority`: `P0` / `P1` / `P2` / `P3`
- `downstream`: `product` / `tech` / `ops` / `none`
- `note`
- `reviewed_at`
- `reviewed_by`

保存确认时，同时更新 `candidate_items.status`，并保留 review 历史。

### 5.7 `export_records`

导出记录。

字段：

- `id`
- `export_date`
- `export_type`: `feedback_report` / `followup_list`
- `file_path`
- `filters_json`
- `item_ids_json`
- `template_version`
- `generated_at`

索引：

- `index(export_date, export_type)`

### 5.8 `collection_runs`

采集运行记录。

字段：

- `id`
- `mode`: `fixture` / `real`
- `started_at`
- `finished_at`
- `status`: `success` / `partial_failed` / `failed`
- `sessions_total`
- `sessions_success`
- `sessions_failed`
- `raw_messages_seen`
- `raw_messages_inserted`
- `raw_messages_duplicated`
- `candidate_items_created`
- `candidate_items_updated`
- `error_code`
- `error_message`

工作台顶部的“最后采集、状态、失败原因”从本表读取。

## 6. 流程设计

### 6.1 定时采集

入口：

- 后台 scheduler 每 30-60 分钟触发。
- 页面“立即采集”按钮触发。

流程：

1. 读取配置和白名单会话。
2. 写入 `collection_runs.started_at`。
3. 调用 `wx_cli_adapter.fetch_messages()`。
4. 对白名单外消息直接丢弃，不进入 `raw_messages`。
5. 写入原始消息并按 `dedupe_key` 去重。
6. 对新增或近期窗口消息执行规则抽取。
7. 更新 `collection_runs` 统计。
8. 页面刷新采集状态。

### 6.2 去重入库

原始消息去重必须发生在抽取前。

候选事项去重在规则抽取后发生：

- 同一 `aggregate_key` 已存在时，只追加证据消息并更新 `last_seen_at`。
- 不重新创建事项编号。
- 人工已驳回的事项再次出现时，保留驳回状态，但可在 UI 上显示“驳回后又出现新证据”。

### 6.3 规则抽取

第一版规则抽取只做保守候选，不做自动结论。

规则来源：

- 关键词：需求、能不能、希望、建议、报错、登录不了、转圈、明天回复、确认一下等。
- 会话配置：客户、渠道、模块。
- 发送方身份：我方、客户方、渠道方、未知。
- 风险关键词：报价、合同、金额、投诉、赔偿、退款、隐私、身份证、手机号等。

输出 5 类事项：

- 客户需求：希望新增/调整功能。
- 问题 / bug：报错、无法使用、异常现象。
- 咨询：询问操作、规则、状态。
- 沟通结论：明确达成一致或形成下一步共识。
- 待我方跟进：出现时间承诺、回复要求、我方待处理动作。

### 6.4 人工审阅

工作台默认筛选：

- 日期：当天
- 状态：待确认
- 会话：全部白名单

右侧表单保存字段：

- 状态：待确认 / 成立 / 驳回
- 负责人
- 优先级
- 下游：产品 / 技术 / 运营 / 暂不同步
- 备注

保存后：

- 写入 `manual_reviews`
- 更新 `candidate_items.status`
- 列表即时刷新

### 6.5 日报导出

导出范围：

- 默认导出当天 `pending` 和 `confirmed` 候选。
- `rejected` 默认不进入日报，可在导出预览中勾选“包含已驳回”用于排查。
- 风险项必须进入“需要人工确认的风险项”区，不进入已确认结论区。

日报章节：

- 运行概览
- 客户需求
- 问题 / Bug
- 咨询
- 沟通结论
- 待我方跟进
- 风险项 / 待人工确认

### 6.6 待办导出

待办只来自：

- 已确认事项
- 待确认但带有高风险或明确“需我方跟进”的事项

待办字段：

- 事项编号
- 客户 / 渠道
- 标题
- 负责人
- 优先级
- 下游同步对象
- 截止时间：第一版留空，由人工补

## 7. 风险边界与安全策略

- 本地优先：客户原文只保存在本机 SQLite 与本机 Markdown 导出。
- 无外发：第一版不调用外部 LLM、云端 API、Webhook、企微接口。
- 无自动回复：不向微信、客户群、渠道群、内部群发送任何消息。
- 无正式写入：不写正式日报、不写正式待办池、不写 Obsidian 正式区。
- 风险保守：报价、合同、金额、投诉、敏感信息、需对外回复的内容一律标记风险，默认待确认。
- 白名单硬边界：白名单外消息不得进入日报，最好也不落库；如为了排障短暂记录，也必须只记录统计，不存原文。
- 失败可见：`wx-cli` 不可用、权限不足、解析失败、超时必须在顶部状态条展示，不允许静默成功。

- 图片、语音、文件解析。

### 8.2 开发助手第二棒

任务目标：接入真实模式适配层与连接测试。

建议范围：

- `wx_cli_adapter.py` 增加真实命令执行与解析。
- 配置页增加连接测试结果展示。
- `collection_runs` 记录真实模式失败原因。
- 文档补充 Windows 上 `wx-cli` 路径配置与初始化前置条件。

验收标准：

- 没有 `wx-cli` 时能明确显示 `missing_binary`。
- `wx-cli` 输出不可解析时显示 `parse_error` 并保留旧数据。
- 真实模式失败不会污染 fixture 数据，也不会清空历史候选。
- 可用 fixture 测试模拟真实模式错误分支。

### 8.3 开发助手第三棒

任务目标：Windows 长期挂机部署材料。

建议范围：

- `scripts/windows/start_server.ps1`
- `scripts/windows/install_task.ps1`
- `docs/windows-deploy.md`
- 日志目录与滚动策略。

验收标准：

- 文档能指导把后台放到 Windows 固定目录运行。
- 任务计划程序示例清楚区分“开机启动后台”和“定时采集由后台调度”。
- 不要求把当前 Mac 变成 Windows 服务。

## 9. 测试审查助手后续验收重点

测试审查助手应重点验证：

- 白名单边界：白名单外 fixture 消息不入库、不导出。
- 去重边界：同一时间窗口重复采集不重复生成原始消息或候选事项。
- 风险边界：报价、合同、金额、投诉、敏感信息、需对外回复只进风险候选。
- 人工确认：确认、驳回、待确认状态可保存，刷新后不丢。
- 导出内容：日报与待办清单只使用本地数据，格式符合产品原型。
- 失败提示：`wx-cli` 缺失、解析失败、超时、权限不足都有可见提示。
- 降级行为：真实采集失败不清空已有数据，仍可审阅和导出历史事项。
- 本地安全：没有外部网络调用，没有自动回复入口，没有正式待办池写入。
- Windows 兼容：路径不硬编码 Mac 专属路径，配置支持 Windows 绝对路径。

## 10. 是否需要初始化 git / 项目结构

建议需要。

理由：

- 当前目录不是 git 仓库，无法稳定追踪后续多固定线程改动。
- 第一棒开发会新增较多文件，必须有 `.gitignore` 防止真实 SQLite、导出 Markdown、日志和真实配置误入版本控制。
- 方案文档、状态卡、需求箱属于项目协作资产，适合进入 git。

建议由监工明确派开发助手第一棒时执行：

```bash
git init
git add AGENTS.md 开发/ .gitignore README.md pyproject.toml config fixtures src tests
```

注意：真实数据目录、真实配置和导出物不得加入 git。
