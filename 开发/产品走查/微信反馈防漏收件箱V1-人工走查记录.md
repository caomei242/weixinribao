# 微信反馈防漏收件箱 V1 人工走查记录

记录时间：2026-05-18 15:31 CST
记录人：产品助手
状态：走查中，暂不发监工，等用户一条龙走完后统一汇总返工包。

## 走查原则

- 按用户真实操作闭环记录，不按开发功能点记录。
- 每一步只记：用户要做什么、页面实际给了什么、哪里反人类、建议怎么改。
- 暂不向监工线程发送回报，等本记录收齐后一次性整理。
- 不记录真实微信消息正文、候选正文、草稿日报正文、真实会话列表、wxid、key、salt、真实 DB 路径或 daemon 原始日志。

## Step 1：顶部状态 / 自动抓取是否透明

用户目标：一眼知道系统有没有在抓、抓的是哪段、上次什么时候抓、下次什么时候抓、现在有多少原始消息和候选。

用户反馈：

- 用户截图反馈：`什么都没看到`。页面顶部实际有一长串技术状态文字，但用户无法从中一眼判断系统是否在自动抓取、是否每 30 分钟跑、上次抓取成功还是失败、下次什么时候抓、草稿日报是否已生成。
- 顶部显示了模式、窗口、最后采集、状态、错误码、连接、会话数、wx-cli 状态等信息，但全部挤在一行，像开发日志，不像产品状态。
- 顶部右上角按钮有 `试读`、`刷新状态`、`生成草稿`、`转述摘要`、`更多`，但没有一个主状态卡明确告诉用户“现在该点哪个”。
- 画面中出现真实客户配置值，走查记录不摘录该值；这类信息后续应只在本机 UI 内展示，不应进入监工回报或日志正文。

初步判断：

- 不合格。信息不是没有，而是表达方式反人类：用户看见的是技术字段堆叠，不是“防漏收件箱今天有没有正常工作”的状态判断。
- `状态：failed` 和 `错误：real_read_disabled` 与页面同时显示 `原始消息 50`、`候选 3` 并存，会让用户更糊涂：到底是失败了，还是已经有可用试读结果。
- 未看到“自动抓取：开启 / 关闭”“抓取频率：手动 / 每 30 分钟”“上次成功抓取”“下次计划抓取”这些人话字段。

建议返工：

- 首屏顶部必须改成 4-6 个大状态卡：`自动抓取`、`上次成功抓取`、`下次计划抓取`、`本次原始消息`、`候选事项`、`草稿日报`。
- 技术字段如 mode、error_code、wx-cli、binary、sessions 放到“诊断详情 / 更多”里，默认别挡主线。
- `real_read_disabled` 要翻译成人话：例如 `真实读取开关未开启，本次只显示最近一次试读结果`。
- 如果有历史 50 条结果但本次抓取失败，页面要明确拆开：`最近一次可用结果：50 条` 和 `本次抓取：失败`，不能混在一起。
- 首屏给一个明确下一步按钮：如果未开启真实读取，主按钮应是 `去开启试读`；如果已有 50 条，主按钮应是 `查看 50 条消息`；如果候选未确认，主按钮应是 `处理 3 条候选`。

## Step 2：试读消息 / 50 条原始明细

用户目标：先看 50 条原始消息，知道谁、几点、说了什么。

用户反馈：

- 用户截图反馈：没有看到 50 条完整明细，只看到左侧露出的少量原始消息卡片。
- 试读消息区文案写 `最近 50 条原始消息`，但页面没有明显显示 `当前展示 1-50 / 共 50`、分页、滚动进度、加载更多或按发送人 / 时间筛选。
- 原始消息卡片能看到时间、发送人标签、消息内容、类型、关联候选和风险状态，但用户无法确认是不是完整 50 条。
- 页面中部候选收件箱在当前筛选下显示 0，提示要切换到 `最近真实试读`，这会打断用户从 50 条原始消息到候选事项的理解。

初步判断：

- 不合格。虽然页面可能有滚动区域，但用户第一眼没有“我现在正在看 50 条完整原始消息”的确定感。
- 50 条明细应该是这个产品的核心信任来源，不能让用户靠猜、靠滚、靠开发解释。
- 当前信息架构容易让用户以为只读到了屏幕上这几条，而不是完整 50 条。

建议返工：

- 试读消息区顶部必须显示：`共 50 条，当前显示 1-50` 或 `共 50 条，当前显示前 N 条，继续向下滚动`。
- 增加明显的列表工具条：时间排序、按发送人筛选、只看未关联候选、只看有风险、搜索关键词。
- 如果只加载部分消息，必须有 `加载更多` 或虚拟列表进度，不能让用户误以为只采到了几条。
- 候选收件箱里 `当前工作台 / 最近真实试读` 的切换逻辑要更人话：在用户从试读消息进入时，默认应展示最近真实试读候选，不要让中间栏空着。

## Step 3：发送人识别 / 微信名与人工映射

用户目标：点开消息后能知道这个人是谁，缺微信名时能手动映射。

用户反馈：

- 用户截图反馈：选择发送人后，把人工身份保存为 `我方`，页面提示 `saved`，但发送人列表和左侧消息卡仍显示旧身份，用户感知为“保存了没效果”。
- 右侧有 `人工身份`、`人员 / 备注名`、`保存发送人映射`，保存后有成功提示，但没有把当前选中发送人的展示身份即时刷新。
- 发送人来源链显示若干聚合发送人及条数，但每个聚合项没有清楚区分 `系统识别身份` 和 `人工覆盖身份`。

初步判断：

- 不合格。保存动作即使后端成功，只要列表和消息卡没有立刻变，用户就会认为没保存。
- 这里缺的是反馈闭环：保存前是什么、保存后变成什么、会影响哪些消息和候选，都没讲清楚。
- `resolved` 这类技术状态对用户没有帮助，应换成人话状态。

建议返工：

- 保存发送人映射后必须即时刷新：发送人列表、左侧原始消息卡、候选详情里的发送人身份都要同步变成新身份。
- 保存提示不要只写 `saved`，要写人话：`已把该发送人标为我方，影响 25 条消息`。
- 聚合项应显示两层身份：`系统识别：客户方`、`人工修正：我方`；如果人工修正存在，以人工修正作为主展示。
- 保存后给用户一个可撤销入口：`撤销本次映射` 或 `改回客户方`。
- 如果需要刷新页面才生效，页面必须明说；但产品上最好不要要求刷新。
- 我方人员应作为全局身份库生效：只要某个名字 / 别名被标成我方，在所有群、所有消息、所有候选、草稿日报和转述摘要里都应统一识别，不应每个会话重复配置。

## Step 4：候选收件箱 / 为什么抽成候选

用户目标：看 3 条候选时能知道它们来自哪几条原始消息，凭什么被抽出来。

用户反馈：

- 用户反馈：不知道为什么抽它，也不知道类型是什么。
- 截图中候选卡有编号、状态、来源、模块、建议等信息，但没有一个明确区域说明 `抽取原因`。
- 右侧 `候选来源链` 只是展示关联来源，不等于解释为什么该消息被抽成候选。
- 当前候选正文和来源里出现真实内容 / 标识符，走查记录不摘录原文或标识符值。

初步判断：

- 不合格。候选事项必须让用户看懂“为什么系统觉得它需要处理”，否则用户只能盲审。
- `来源：最近真实试读` 和 `建议：tech / ops` 这类字段对用户帮助有限，不能替代抽取理由。
- 当前候选卡缺少人话解释，例如“命中问题/需求/待跟进关键词”“出现明确指派/时限/未解决语义”“来自某几条原始消息”。

建议返工：

- 每条候选卡增加 `为什么抽它` 区块，用 1-2 句人话说明抽取理由。
- 右侧详情增加 `证据链`：关联原始消息条数、关键触发点、是否有回复闭环、是否仍待确认。
- 来源链不要只展示一条卡片，要支持点击跳回左侧对应原始消息，并高亮关联消息。
- 对真实标识符做 UI 脱敏展示，默认不要把 wxid 一类标识符直接露给用户；需要诊断时放到“技术详情”。

## Step 5：人工确认 / 驳回 / 改类型

用户目标：每条候选能顺手确认、驳回、改类型或补充说明。

用户反馈：

- 用户反馈：类型是什么没看到，也没看到能不能改。
- 用户继续反馈：没有看到确认 / 驳回 / 改类型入口，而且有些信息看不到。
- 截图中候选卡只有类似编号前缀、模块和建议字段，用户无法直接理解它到底是需求、Bug、咨询、结论还是待跟进。
- 中间栏顶部有类型筛选按钮，但这只是筛选，不是当前候选的类型编辑入口。
- 当前可见区域没有清楚的 `确认`、`驳回`、`改类型`、`补充说明` 操作闭环。
- 当前三栏布局下，右侧详情与发送人识别 / 群档案混在同一个滚动区域，关键信息和操作按钮可能被挤到不可见位置；用户不知道该滚哪一栏。

初步判断：

- 不合格。人工确认是主线关键步骤，不能藏在用户需要猜的位置。
- 类型如果用编号前缀表达，用户看不懂；必须直接显示中文类型。
- 筛选按钮和编辑按钮混在一起，会让用户误以为不能改类型。
- 不合格程度加重：候选详情的核心动作没有固定在用户视野内，导致“候选收件箱”只能看，不能处理。

建议返工：

- 每张候选卡直接显示中文类型标签：`需求 / Bug / 咨询 / 结论 / 待跟进`。
- 点开候选后，右侧详情必须固定出现：`确认`、`驳回`、`改类型`、`补充说明`、`保存`。
- `改类型` 应是下拉框或分段按钮，当前类型高亮，保存后候选卡立即同步。
- 确认后要显示影响：`已确认，将进入草稿日报 / 转述摘要`；驳回后要显示 `已驳回，不再进入草稿日报`。
- 如果当前处于 `最近真实试读` 来源，还需要明确提示：`确认前需先加入待确认工作台` 或直接提供一键确认，不要让用户理解两个池子的差别。
- 候选详情区应改成固定结构：顶部是候选摘要和类型，中部是抽取理由与证据链，底部固定悬浮操作条，避免用户滚动后找不到确认按钮。
- 三栏各自滚动时必须有清楚边界；右侧如果内容太多，应分 Tab：`候选详情 / 发送人 / 群档案`，不要全堆在一个长栏里。

## Step 6：群 / 客户打标

用户目标：客户名称、群负责人、业务模块、客户阶段、群类型、常用联系人、回复注意事项能录入、保存、刷新后还在。

用户反馈：

- 用户反馈：不想自己手动打标，希望直接看草莓客户管理系统里的客户打标 / 客户资料来带出。
- 当前配置中心的群 / 客户打标是空表单，要求用户手工填客户名称、群负责人、业务模块、客户阶段、群类型、常用联系人、回复注意事项。
- 只读检查草莓客户管理系统后确认：现有客户管理系统已经沉淀客户页、客户总表、项目页、关系人库，具备可复用字段，不应让用户重复维护。
- 走查记录不摘录真实客户名称、人员姓名、联系方式或关系判断，只记录字段能力。

初步判断：

- 不合格。V1 打标不应是“手工配置中心”，而应该是“从草莓客户管理系统自动匹配 -> 用户确认 / 修正”。
- 当前表单让用户重复录入已有客户系统资料，增加实战成本，和用户“不想截图、不想搬运”的核心痛点冲突。
- `群负责人` 字段语义不清：需要拆清楚是客户侧主联系人、群内常说话的人，还是我方跟进负责人。

建议返工：

- 增加 `从草莓客户管理系统匹配` 主按钮：按群名、会话标识、发送人昵称、客户名称关键词去只读匹配客户页 / 客户总表 / 关系人库 / 项目页。
- 匹配结果必须以候选方式展示，不自动覆盖：`推荐客户`、`匹配依据`、`置信度`、`可一键套用`。
- 字段映射建议：
  - `客户名称`：来自客户页 / 客户总表的客户名。
  - `业务模块`：来自客户业务方向、二级标签、当前需求或活跃项目类型。
  - `客户阶段`：来自客户页当前阶段。
  - `群类型`：由客户类型推断，例如品牌客户、网店店群客户、博主、内部协作等。
  - `常用联系人`：来自客户页当前联系人、关系人库、项目参与人。
  - `回复注意事项`：来自关系人库的适合沟通方式、雷区、不喜欢事项、客户限制条件。
  - `群负责人` 建议改名或拆分为 `客户主联系人` 和 `我方跟进人`。
- 自动匹配只读草莓客户管理系统，不能反向写入客户系统；用户在微信后台修正的群映射只保存到微信项目本地配置。
- 未匹配到时再让用户手填，并支持把本次群映射保存成规则，后续同群自动套用。

## Step 6b：我方人员全局配置

用户目标：我方人员只配置一次，后续所有群、所有消息、所有候选和所有转述都自动识别为我方。

用户反馈：

- 用户反馈：我方人员不要每一次都配置，只要是我方人员的，应该全部地方都写完。
- 当前配置中心的 `我方人员` 是单独空表单，看起来需要用户手工新增人员名称和别名。
- 这和发送人识别里的单条映射割裂：用户在消息里保存某人为我方后，不确定是否进入全局我方人员库。

初步判断：

- 不合格。我方人员是全局身份，不是某个群的配置项。
- 当前设计把 `发送人映射`、`我方人员`、`群 / 客户打标` 分散成多个入口，用户不知道哪个才是权威来源。
- 如果不做全局身份库，后续草稿日报和转述摘要很容易把我方发言误判成客户反馈。

建议返工：

- 建立全局 `我方人员库`：姓名、别名、微信显示名、备注名、常见群名、身份说明。
- 保存发送人映射为 `我方` 时，默认询问或自动同步到全局我方人员库，后续所有会话复用。
- 所有模块统一读这一个身份库：试读消息、候选抽取、发送人识别、草稿日报、转述摘要、风险词判断。
- 配置中心显示当前已配置的我方人员列表，不要只给一个空新增表单。
- 支持从草莓客户管理系统关系人库读取 `内部支持 / 我方 / 草莓主业` 相关人员，自动生成候选我方人员，用户只确认。
- 对同名/别名冲突给提示：例如 `这个别名已属于某某，是否合并？`

## Step 7：草稿日报

用户目标：在前台直接看到草稿日报状态、生成时间、来源、候选数、风险数和正文预览。

用户反馈：

- 用户反馈：没看到想要的草稿日报。
- 截图显示右侧有 `草稿日报 / 机器初稿` 预览框，但数据源为 `workspace`，候选数为 0，正文只有空草稿结构和 `暂无候选条目`。
- 用户此前已经在 `最近真实试读` 下看到 3 条候选，但草稿日报没有自动使用这 3 条候选生成。
- 每日运行时间线显示今日采集 failed、候选审阅 pending、待沉淀草稿 pending，但没有给出用户下一步应该点哪里才能把最近真实试读候选变成草稿。

初步判断：

- 不合格。草稿日报虽然前台有预览区域，但没有接上 V1 主线的 `最近真实试读候选`，用户看到的是空日报。
- `workspace` 这类数据源术语对用户不友好；用户只关心“用最近 50 条生成”还是“用已确认候选生成”。
- 生成草稿前置条件不清楚：到底要先加入待确认、先确认候选，还是可以直接用最近真实试读生成草稿，页面没讲清。

建议返工：

- 草稿日报区必须有清楚的数据源切换：`用最近真实试读生成` / `用已确认候选生成`。
- 当最近真实试读有 3 条候选而当前工作台为 0 时，草稿日报区应主动提示：`发现最近真实试读 3 条候选，可生成试读草稿`，并给一键按钮。
- 生成草稿后顶部状态卡、草稿日报区和转述摘要都要同步显示 `已生成`、生成时间、数据源、候选数、风险数。
- 不要显示 `workspace` 这种内部词，改成人话：`当前工作台候选` / `最近真实试读候选`。
- 空草稿不能只写 `暂无候选条目`，要告诉用户为什么空、下一步怎么做。

## Step 8：转述摘要

用户目标：生成一段能直接复制给客户 / 内部同事看的转述摘要，不像开发导出文件。

用户反馈：

- 用户反馈：不要有的是弹窗、有的是跳转到下面，太麻烦；最好不要跳下面，也不要弹窗，直接固定页变换。
- 用户继续反馈：当然看不懂，页面里的模板、数据源、导出说明和预览都不知道是在干什么。
- 当前 `转述摘要` 以弹窗 / 覆盖层形式出现，和 `试读消息`、`候选收件箱`、`草稿日报` 等页面内跳转 / 下滚行为不一致。
- 弹窗打开后仍能看到背后的页面内容，用户容易迷路：不知道自己是在主流程、配置中心，还是导出工具里。
- 转述摘要里有模板、数据源、导出日期、复选项、Markdown 预览、导出按钮等较复杂操作，不适合做成临时弹窗。
- 页面显示 `每日反馈日报（审阅版）`、`待跟进事项清单`、`可转产品 / 技术摘要`，但没有用用户场景解释“发给谁、什么时候用、会包含什么”。
- 页面显示 `最近真实试读`、`仅导出已确认`、`包含待人工确认`、`风险项单独成区`、`Markdown 预览` 等字段，但没有形成一个自然任务：复制给客户 / 复制给内部 / 留给自己复盘。
- 预览正文仍偏系统报告口吻，包含模板、安全边界等内部字段，不像用户可以直接拿去转述的人话。

初步判断：

- 不合格。转述摘要是 V1 主链路最后一步，不应像辅助工具一样弹出。
- 当前交互范式混乱：主导航有的定位到页面下方，有的打开弹窗，有的改变中间内容，用户每点一次都要重新找位置。
- `转述摘要` 应该和 `试读消息 / 候选收件箱 / 群客户打标 / 草稿日报` 一样，是固定工作区里的一个正式页面。
- 转述摘要的信息架构不合格：它现在像“导出中心”，不是“帮用户把今天客户反馈转述出去”。
- 模板选项是系统视角，不是用户动作视角；用户不知道该选哪个。

建议返工：

- 取消主流程里的弹窗和自动跳到页面下方。左侧主导航点击后，只在右侧固定工作区切换页面。
- 固定布局建议：左侧导航不动，顶部状态不动，中间主工作区随导航切换。
- `转述摘要` 改为固定页：上方是模板和数据源，中间是候选/风险选项，下方是 Markdown 预览，右侧是导出说明。
- `配置中心` 也不要弹窗，改成固定页；需要返回时点左侧其他导航即可。
- 页面不要自动滚动到下方模块；用户点击导航时应看到对应页面首屏，而不是被带到某个半截位置。
- 转述摘要入口改成用户任务，而不是模板名：
  - `给客户回复`
  - `给内部产品 / 技术同步`
  - `给自己留今日复盘`
- 每个任务卡用一句话解释：`适合发给谁`、`包含什么`、`不会包含什么`。
- 预览默认直接展示可复制的人话版本，内部安全说明和模板语义收进详情，不要混进正文主预览。
- 按钮改成人话：`复制摘要`、`下载 Markdown`、`保存到本地 exports`，不要只写 `导出全部 3 份`。

## Step 9：刷新后是否保留

用户目标：刷新页面后，打标、确认结果、草稿日报和摘要状态不丢。

用户反馈：

- 用户反馈：刷新后弹窗就没了。
- 刷新后页面回到首页 / 长页混合状态，之前打开的 `转述摘要` 弹窗状态没有保留。
- 页面显示多个区域进入 `载入中...`，用户不知道是正在恢复数据、失败了，还是要重新操作。
- 刷新后没有保留用户所在的主流程位置，也没有提示 `上次你在转述摘要，可继续`。

初步判断：

- 不合格。主流程不应该依赖弹窗状态；刷新后弹窗消失是浏览器正常行为，但产品不应该把主任务放在这种临时状态里。
- 刷新后至少应恢复当前主导航页、关键筛选、数据源选择和最近操作结果。
- 当前刷新体验会让用户误以为刚才的配置 / 预览 / 选择丢了。

建议返工：

- 主导航页面状态应写入 URL hash / query 或本地状态，刷新后恢复到同一页，例如 `/转述摘要` 或 `#transfer-summary`。
- 取消主流程弹窗后，刷新也应停留在固定页 `转述摘要`，而不是回到首页长页。
- 关键筛选和数据源选择要持久化：最近真实试读 / 当前工作台、是否包含待人工确认、模板选择。
- 载入中状态要有超时和失败提示，不要无限显示。
- 页面顶部增加恢复提示：`已恢复上次位置：转述摘要` 或 `当前显示最近一次试读结果`。

## 补充遗漏：统一候选池 / 数据源口径

用户目标：不需要理解 `最近真实试读`、`当前工作台`、`workspace`、`recent50` 这些内部池子，只知道哪些事项待确认、哪些已进草稿。

补充判断：

- 当前最大隐藏问题是“两套池子”：最近真实试读里有候选，当前工作台可能是 0；草稿日报又默认读 workspace，导致用户看到空日报。
- 这会直接破坏主线：用户明明看到 3 条候选，却在草稿日报 / 转述摘要里看到另一套数据。

建议返工：

- 产品上只暴露一个 `候选收件箱`，内部来源可以有多个，但用户只看统一列表。
- 每条候选显示来源标签即可：`来自最近试读`、`已加入待确认`、`已确认`、`已进草稿`。
- 草稿日报和转述摘要默认使用同一个可见候选列表，不要默认切到另一个空池子。
- 如果必须保留导入动作，文案改成 `把这 3 条加入今日处理`，并在导入后明显显示 `今日处理：3 条`。

## 补充遗漏：每日防漏收口清单

用户目标：每天看一眼就知道“今天还差哪一步”，避免忘了就没有后续。

补充判断：

建议返工：

  - `已试读 50 条`
  - `已识别发送人`
  - `待确认候选 3 条`
  - `已确认 0 条`
  - `草稿日报未生成`
  - `转述摘要未复制 / 未导出`

## 补充遗漏：动作结果和撤销

用户目标：每次保存、确认、驳回、导出后，知道是否成功、影响了什么、能不能撤销。

补充判断：

建议返工：

## 补充遗漏：加载 / 失败 / 诊断分层

用户目标：遇到失败时知道是没开真实读取、服务没连上、没有新消息，还是只是健康检查正常。

补充判断：

- 当前 `载入中...`、`failed`、`real_read_disabled`、`ok` 混在一起，没有恢复路径。
- 30 分钟健康检查和真实消息抓取必须拆开，否则用户会误以为后台在自动抓。

建议返工：

- 把状态拆成三层：
  - `服务健康`：本地后台是否活着。
  - `真实读取`：是否开启、上次读取是否成功、失败原因。
  - `数据结果`：最近一次可用消息 / 候选 / 草稿。
- `载入中...` 超过固定时间要显示失败提示和重试按钮。
- `real_read_disabled` 改成人话，并给下一步：`真实读取关闭，点击试读才会抓取。`
- 如果只是健康检查每 30 分钟跑，页面必须写明：`健康检查每 30 分钟；消息不会自动抓取。`

## 补充遗漏：敏感信息默认隐藏

用户目标：本机能看原文，但转述、日报、状态卡和走查里不要露 wxid、真实 DB、key、salt、技术日志。

补充判断：

- 当前页面中用户可见区域出现技术标识符，普通用户不需要直接看。
- 这类信息放在主线 UI 中会增加理解成本，也增加误复制风险。

建议返工：

- 主流程默认隐藏 wxid / key / salt / DB 路径 / daemon 日志 / 技术错误栈。
- 需要时放到 `诊断详情`，并明确 `仅本机排障使用，不进入转述摘要`。
- 转述摘要和草稿日报默认使用脱敏版，复制前再次提示不含真实原文和技术标识符。

## 补充遗漏：全局文案不是给用户看的

用户目标：页面文字要像一个每天帮我防漏的工作台，而不是开发调试台、审查报告或字段说明书。

用户反馈：

建议返工：

  - `workspace` -> `今日处理区`
  - `real_trial` -> `最近试读`
